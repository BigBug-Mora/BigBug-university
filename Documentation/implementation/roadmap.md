# EstateFlow MVP implementation roadmap

Build the documented four-agent marketplace for houses, apartments, and land. A seller can prepare and publish a listing, a buyer can find it and ask questions, and the seller can answer ordinary inquiries or grant access to selected private details. Market intelligence, pricing comparables, and viewing appointments belong to the wider product scope. [MVP workflows and acceptance examples](../mvp/agent-details/agent-details.md) · [Complete product scope](../complete%20scope/complete-scope.md)

## How to use this roadmap

- The phase numbers suggest a build order. The dependencies name the behavior each phase needs. Use fictional fixtures or mocks for adjacent features so each phase can be verified on its own.
- Open the phase plan before writing code. Give each phase a folder and a plan when it is ready for implementation. Put small steps in the phase plan and use linked subphase files when the work can be handed off and verified separately.
- Tick a phase after its acceptance check passes. Record the evidence in that phase’s plan. When scope or order changes, update the affected plans and log what changed, why, and which downstream phases are affected. Name the destination for moved work.
- Use the [repository layout](repository-layout.md) to place code. Use the [container design](../mvp/containers/containers.md), [database contracts](../mvp/database/contracts.md), and [CI design](../mvp/ci/cd/ci.md) to resolve ownership and behavior. Record discrepancies in the active plan.

## Phases

- [x] **01 · Development foundation**. Establish the local runner, first PostgreSQL migration, fixtures, CI, and shared AWS development setup. **Depends on** the existing MVP design. **Accept when** a clean checkout can migrate and load a disposable database, the checks pass in CI, and shared AWS dependencies are verified (originally scoped for two teammates; finalized on 2026-11-27 with single-operator verification using the shared `Estateflow` IAM profile per owner decision). [Phase 1 plan](phase-01/phase1.md)

- [x] **02 · Identity and account access**. Establish Auth.js and Cognito sign-in, stable account mapping, and verified actor context across services. Require buyers to sign in before searching or opening a listing. **Depends on** 01. **Accept when** a returning Cognito user resolves to the same account and a protected endpoint rejects an unverified actor. Verify with test identities in CI and a deliberate Cognito smoke test. [Phase 2 plan](phase-02/phase2.md)

- [ ] **03 · Seller listing drafts**. Build the seller editor and Property operations for typed facts, revision saving, and encrypted private details. **Depends on** 01–02. **Accept when** a seller saves and reopens a draft, zero and unknown values remain distinct, a retry preserves the intended revision, and a different account is denied. [Property service](../mvp/containers/property-service/property-service.md) · [Listing revisions](../mvp/database/contracts.md#listing-revisions-and-publication)

- [ ] **04 · Showcase preview and publication**. Build preview, explicit publish, and the published listing page for signed-in buyers using an authored showcase fixture. Settle how the page handles a listing with no photos. **Depends on** 03. **Accept when** the seller publishes a matching revision and showcase, saves a private price edit, and the published page keeps the original price until the seller publishes the updated pair. [Publication contracts](../mvp/database/contracts.md#listing-revisions-and-publication) · [Frontend](../mvp/containers/frontend/frontend.md) · [UI design](../mvp/containers/frontend/ui.md)

- [ ] **05 · Structured search and navigation**. Let signed-in buyers filter published listings and restore query and results when returning from a listing. **Depends on** 04, with published fixtures usable for search tests. **Accept when** fixtures distinguish confirmed, false, and unknown vehicle access, a per-area land price is evaluated by its calculated total, and Back to Search restores the prior results. [Buyer search](../mvp/containers/agent-api/buyer-agent.md#search-mode) · [Public search schema](../mvp/database/schema.md)

- [ ] **06 · Photos and galleries**. - [ ] **07 · Durable background jobs**. Implement acceptance, dispatch, worker claims, results, and recoverable status with a deterministic test job. Define timeouts and configure distinct execution scopes for local stacks and hosting. **Depends on** 01–03. **Accept when** a job survives broker downtime, duplicate delivery yields one logical result, interrupted work recovers under the retry rules, and a second scope cannot execute the first stack’s jobs. [Database job contracts](../mvp/database/contracts.md#background-jobs-and-hosted-cutover) · [Dispatcher](../mvp/containers/agent-dispatcher/agent-dispatcher.md) · [RabbitMQ](../mvp/containers/rabbitmq/rabbitmq.md) · [Worker](../mvp/containers/agent-worker/agent-worker.md)

## Decision log

- Initial plan uses small, verifiable service boundaries and a detailed plan for Phase 1. Later phase plans will use the files, commands, and interfaces established by earlier phases.
- Start shared AWS dependencies in Phase 1 and package services as they land. Reserve hosted application deployment for Phase 17, consistent with the documented development strategy.
- On 2026-11-27, the owner standardized on a single shared `Estateflow` IAM identity (`estateflow-dev` CLI profile) and waived the two-teammate machine check for Phase 01 acceptance. Phase 15 will still rehearse the two-role seller/buyer workflow using the existing Cognito buyer and seller test accounts.
